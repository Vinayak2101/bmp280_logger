# Deployment guide — BMP280 logger + CloudPanel collector

This is the exact procedure for **this** project: the ESP32 board in your hand, the
[github.com/Vinayak2101/bmp280_logger](https://github.com/Vinayak2101/bmp280_logger) repo,
and a CloudPanel VPS. Every command is copy-pasteable; every step has an expected output so
you can tell success from failure without guessing.

## Values used in this guide

Fill the blanks once, then the rest of the document reads literally.

| Item | Value | Where it comes from |
| --- | --- | --- |
| Repository | `https://github.com/Vinayak2101/bmp280_logger.git` | fixed |
| Collector listen address | `127.0.0.1:8787` | set by `vps/install.sh` |
| Collector service | `bmp280-webhook` | systemd unit name |

| ESP32 LAN address | `192.168.0.156` | your board (mDNS: `esp32-bmp280.local`) |
| **Your domain** | `_______________________` | e.g. `sensors.example.com` |
| **Your VPS IPv4** | `_______________________` | `ip -4 addr` on the server |

## 0. Prerequisites

- A CloudPanel VPS you can SSH into as root (CloudPanel v2 on Ubuntu 22.04/24.04 or Debian 12).
- A DNS provider where you can add an **A record**.
- The ESP32 already flashed, on the LAN, reachable at `http://192.168.0.156/`.
- Note: the collector needs **no** PHP, Node, or Python runtime from CloudPanel — it is a
  single standard-library Python script started by systemd.

---

## 1. DNS

Create an **A record**:

```
sensors.example.com.   A   <your VPS IPv4>
```

Wait for propagation, then confirm **before** touching CloudPanel (Let's Encrypt fails on a
domain that doesn't resolve yet):

```bash
dig +short sensors.example.com
```

Expected: your VPS IPv4, nothing else. If it is empty, stop — do not create the site yet.

## 2. CloudPanel: site + certificate

### 2.1 Choose the site type

CloudPanel's **Sites → Add Site** asks for a type. For this collector:

| Option shown | Use it? | Reason |
| --- | --- | --- |
| **Reverse Proxy** | ✅ recommended | nginx forwards the whole vhost to `127.0.0.1:8787`; simplest, and CloudPanel will not fight your config |
| **Static Site** | ✅ fallback | smallest vhost; you add a `location /sensors/` block yourself |
| Node.js / Python / PHP | ❌ | installs a runtime and an app process you don't need |

Do not pick Node.js or Python: CloudPanel expects a gunicorn/pm2 app on a port and will create
extra users and services.

### 2.2 Create it

**Reverse Proxy route:**

1. Sites → Add Site → **Reverse Proxy**
2. Domain: `sensors.example.com`
3. Reverse proxy URL: `http://127.0.0.1:8787`
4. Create

**Static Site route:**

1. Sites → Add Site → **Static Site**
2. Domain: `sensors.example.com`
3. Create (leave the document root as CloudPanel suggests)

### 2.3 Issue the TLS certificate

Sites → `sensors.example.com` → **SSL/TLS** → **Actions** → **New Let's Encrypt Certificate** →
Create. Wait for the green check.

Verify from your laptop:

```bash
curl -sI https://sensors.example.com | head -1
```

Expected: `HTTP/2 200` (reverse proxy) or `HTTP/2 200`/`404` (static). A certificate error here
means the cert was issued for a different hostname — fix that before continuing, because the
ESP32 will fail on TLS otherwise.

> CloudPanel rewrites `/etc/nginx/sites-enabled/<domain>.conf` whenever you change SSL, site
> type, or vhost settings. Any manual edit in that file can be silently dropped. This is why
> the Reverse Proxy route is recommended: it needs no manual edit at all.

## 3. Install the collector

```bash
ssh root@<vps-ip>

# git is present on CloudPanel images; if not: apt-get update && apt-get install -y git
git clone https://github.com/Vinayak2101/bmp280_logger.git /root/bmp280_logger
cd /root/bmp280_logger
bash vps/install.sh
```

Expected output (values differ):

```
== service ==
active
== health ==
{"ok":true,"count":0}
== token (keep secret) ==
6f1c...48-hex-chars
```

**Write the token down.** It is also stored in `/etc/default/bmp280-webhook`.

What the script did, in order:

1. created a `bmp280` system user (`nologin`, home `/var/lib/bmp280`)
2. copied `webhook.py` to `/opt/bmp280/webhook.py`
3. generated a random token into `/etc/default/bmp280-webhook` (mode 600), **only if absent**
4. installed and enabled `bmp280-webhook.service`
5. printed health and token

The script is idempotent: re-running never wipes the database and never regenerates the token.

### 3.1 Verify the service

```bash
systemctl status bmp280-webhook --no-pager
```

Expected: `Active: active (running)`.

```bash
curl -s http://127.0.0.1:8787/health
```

Expected: `{"ok":true,"count":0}` — `count` is the number of stored readings.

```bash
ss -ltnp | grep 8787
```

Expected: `LISTEN 0 128 127.0.0.1:8787 ... users:(("python3",pid=...,fd=...))`.
It must be bound to **127.0.0.1**, never `0.0.0.0` — nginx is the only public entry point.

```bash
ls -l /var/lib/bmp280/
```

Expected: `bmp280.db` (created on first request or immediately by the script).

## 4. Expose it through nginx

### 4.1 Reverse Proxy site (recommended)

Nothing to do — CloudPanel already proxies the vhost to `127.0.0.1:8787`. Skip to §5 and use
`https://sensors.example.com/ingest` as the device URL.

### 4.2 Static site

Find the vhost:

```bash
ls /etc/nginx/sites-enabled/
```

Edit the one matching your domain and insert the block into the **`server { }` that listens on
443** (here shown with CloudPanel's typical surrounding lines, so you can see where it goes):

```nginx
server {
    listen 443 ssl;
    server_name sensors.example.com;

    # ... CloudPanel's ssl_certificate / root / etc ...

    # >>> add this block <<<
    location /sensors/ {
        proxy_pass http://127.0.0.1:8787/;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 30s;
        proxy_connect_timeout 5s;
    }
    # >>> end <<<

    location / {
        try_files $uri $uri/ =404;
    }
}
```

The trailing slash on `proxy_pass http://127.0.0.1:8787/;` is required: it strips `/sensors/`
before forwarding, which is what the Python handler expects.

Reload only after a successful syntax check:

```bash
nginx -t && systemctl reload nginx
```

Expected: `syntax is ok` then `test is successful`.

## 5. Prove the endpoint works

Use the URL that matches your site type:

| Site type | Ingest URL |
| --- | --- |
| Reverse Proxy | `https://sensors.example.com/ingest` |
| Static | `https://sensors.example.com/sensors/ingest` |

```bash
TOKEN=<your token>
BASE=https://sensors.example.com          # static: add /sensors

curl -s "$BASE/health"                     # {"ok":true,"count":0}

curl -s -X POST "$BASE/ingest" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"device":"curl-test","seq":1,"temp_c":25.4,"press_hpa":1009.2,"rssi":-50}'
# {"ok":true,"id":1}

curl -s "$BASE/latest?token=$TOKEN"
```

Expected `latest`:

```json
{"ok":true,"reading":{"id":1,"device":"curl-test","seq":1,"ts":null,
 "received_at":"2026-11-24T14:20:11Z","uptime_s":null,"temp_c":25.4,
 "press_hpa":1009.2,"sea_level_hpa":null,"altitude_m":null,"rssi":-50,"heap":null}}
```

Negative test — confirm the token actually protects the endpoint:

```bash
curl -s -o /dev/null -w '%{http_code}\n' -X POST "$BASE/ingest" \
  -H 'Content-Type: application/json' -d '{"temp_c":20,"press_hpa":1000}'
```

Expected: `401`.

## 6. Point the ESP32 at it

On your laptop, open `http://192.168.0.156/` → **Settings**:

| Field | Value |
| --- | --- |
| Webhook URL | `https://sensors.example.com/ingest` (static: `/sensors/ingest`) |
| Bearer token | the token from §3 |
| Reporting interval | `30` |
| Reference altitude | your real elevation in metres (see §9.2) |

Press **Save**, then **Send test**.

Expected in the browser toast: `Webhook OK (HTTP 200)`.

Confirm on the server:

```bash
curl -s "https://sensors.example.com/latest?token=$TOKEN"   # device should read esp32-bmp280
sqlite3 /var/lib/bmp280/bmp280.db 'SELECT COUNT(*), MAX(received_epoch) FROM readings;'
```

Then watch a full interval go by (30 s) and check the count increments:

```bash
watch -n 5 "sqlite3 /var/lib/bmp280/bmp280.db 'SELECT COUNT(*) FROM readings;'"
```

If the dashboard shows **Queued: n** climbing instead of **Delivered** climbing, the device
cannot reach the endpoint — see §10.

## 7. Long-term operation

```bash
systemctl enable bmp280-webhook     # already done by the script; survives reboot
journalctl -u bmp280-webhook -f     # live log: every accepted POST and every 401
```

Log rotation is handled by journald (no files to rotate). The SQLite DB grows ~50 kB/day at a
30 s interval (~18 MB/year).

### 7.1 Backup

```bash
mkdir -p /root/backups
sqlite3 /var/lib/bmp280/bmp280.db ".backup '/root/backups/bmp280-$(date +%F).db'"
```

Run nightly via cron:

```bash
echo '17 3 * * * sqlite3 /var/lib/bmp280/bmp280.db ".backup '\''/root/backups/bmp280-$(date +\%F).db'\''"' \
  >> /etc/cron.d/bmp280-backup
```

`.backup` is safe on a live WAL database — do not `cp` the `.db` file while the service runs.

### 7.2 Restore

```bash
systemctl stop bmp280-webhook
cp /root/backups/bmp280-2026-11-24.db /var/lib/bmp280/bmp280.db
chown bmp280:bmp280 /var/lib/bmp280/bmp280.db
rm -f /var/lib/bmp280/bmp280.db-wal /var/lib/bmp280/bmp280.db-shm
systemctl start bmp280-webhook
```

### 7.3 Upgrade

```bash
cd /root/bmp280_logger && git pull
install -m 755 vps/webhook.py /opt/bmp280/webhook.py
systemctl restart bmp280-webhook
```

The token and database are outside the repo, so upgrades never disturb them.

### 7.4 Rotate the token

```bash
NEW=$(openssl rand -hex 24)
sed -i "s/^BMP280_TOKEN=.*/BMP280_TOKEN=$NEW/" /etc/default/bmp280-webhook
systemctl restart bmp280-webhook
echo "$NEW"     # then paste into the dashboard and Save
```

Old token stops working immediately; the device keeps queueing (up to 20 samples) until you
update it.

### 7.5 Uninstall

```bash
systemctl disable --now bmp280-webhook
rm -f /etc/systemd/system/bmp280-webhook.service
systemctl daemon-reload
rm -rf /opt/bmp280 /etc/default/bmp280-webhook
# database left behind on purpose: /var/lib/bmp280
```

## 9. Correctness notes

### 9.1 Timestamps

Two clocks are stored on purpose:

- `sensor_ts` — from the ESP32's NTP clock; `null` until it syncs (a few seconds after joining Wi-Fi).
- `received_epoch` — server time, always present; this is the authoritative ordering key.

If `sensor_ts` is null forever, the ESP32 has no internet route (DNS blocked) — the dashboard
shows `ts: null` and the payload still arrives.

### 9.2 Sea-level pressure

`sea_level_hpa` is computed **on the device** from the configured reference altitude:

```
P0 = P / (1 - h/44330)^5.255
```

With `altitude_m = 0` the column equals the raw pressure. Set it to your actual elevation
(your current reading implied ~24 m). A wrong value shifts sea-level pressure roughly 12 hPa
per 100 m — it does not affect `temp_c` or `press_hpa`.

### 9.3 Duplicates

The device re-sends a sample if the response is lost after the server stored it. Duplicates are
therefore possible; deduplicate with:

```sql
SELECT COUNT(*) FROM (SELECT device, sensor_ts, temp_c FROM readings
                      GROUP BY device, sensor_ts, temp_c HAVING COUNT(*) > 1);
```

## 10. Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Device toast `Webhook failed (HTTP -1)` | TCP/TLS connect failed: wrong host, DNS, or firewall | `curl -sv https://<domain>/ingest` from your laptop; check §1 DNS |
| Device toast `Webhook failed (HTTP 401)` | token mismatch or missing `Bearer ` | re-copy token from `/etc/default/bmp280-webhook`, save again |
| Device `HTTP 404` | wrong path (`/sensors/` missing on a static site, or present on a reverse-proxy site) | match §5 table exactly |
| Device `HTTP 502` | nginx reached but the collector is down | `systemctl status bmp280-webhook`; `journalctl -u bmp280-webhook -n 50` |
| `curl` from laptop works, device fails | device on 2.4 GHz guest network with client isolation, or router blocks outbound | test from a phone on the same Wi-Fi |
| Browser page `/` returns 401 | token missing from URL | open `https://<domain>/?token=<TOKEN>` |
| `install.sh` prints `python3 missing` | minimal image | `apt-get update && apt-get install -y python3` |
| `{"ok":false,"error":"unauthorized"}` on `/health`? | never — `/health` is public by design | verify nginx points at 8787, not at a static root |
| Manual nginx block disappeared | CloudPanel rewrote the vhost on an SSL/site change | re-add it, or switch the site to Reverse Proxy |
| Certificate error on the device only | Let's Encrypt chain not yet issued when the device saved the URL | issue the cert first (§2.3), then press **Send test** again |
| `count` in `/health` stops growing | device offline or Wi-Fi down | `curl http://192.168.0.156/data` from your laptop |

Useful one-liners:

```bash
journalctl -u bmp280-webhook -n 100 --no-pager
tail -f /var/log/nginx/access.log | grep ingest
ss -ltnp | grep 8787
sqlite3 /var/lib/bmp280/bmp280.db 'SELECT COUNT(*) FROM readings;'
curl -s "http://192.168.0.156/data"          # device-side status
curl -s "http://192.168.0.156/scan"          # device-side I2C diagnostics
```

## 11. Security posture

- The collector binds to `127.0.0.1` only; the sole public surface is the nginx proxy.
- Every write requires a bearer token, compared in constant time; `/health` is the only
  unauthenticated route.
- The token lives in `/etc/default/bmp280-webhook` (mode 600, root) and in the ESP32's NVS.
- The device uses an **unverified TLS client** (`setInsecure`) because the ESP32 core's CA store
  cannot validate most Let's Encrypt chains. The bearer token, not TLS, authenticates the POST.
  Consequence: a network attacker could read telemetry values in transit — acceptable for
  weather data, not for anything sensitive.
- `firmware/secrets.h` must never be committed; it is in `.gitignore`. If a Wi-Fi password is
  ever pushed, rotate the password — deleting the file does not remove it from history or from
  anyone's clone.
